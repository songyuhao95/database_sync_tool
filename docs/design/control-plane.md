# Phase-one control plane

Phase one uses the `cdc` CLI, the deployed Apache Kafka 3.7.2 cluster through Rust `rdkafka` 0.39.0, Kafka control and audit topics, and the target metadata table. It relies on the Kafka 3.7 transactional protocol and does not require Kafka 4 transaction protocol version 2. It has no Web UI, public REST API, automatic scheduler, or built-in user directory.

## Configuration

Operators author a strict, versioned `cdc.toml`. Unknown fields are rejected. `cdc config init` writes generated UUIDs for Sources, Sinks, Capture Streams, Capture Stream Generations, and Replication Routes back into the file; `cdc config apply` refuses an entity without an explicit ID. Names are mutable labels, but IDs are immutable and never reused. A Route binds one exact generation and cannot follow a later generation implicitly.

Capability Qualifications are held in a release-owned Capability Manifest embedded in the connector binary, not fetched at runtime or authored by operators. Its deterministic canonical bytes have a SHA-256 content digest that the connector checks at startup. The digest identifies the manifest and catches accidental mismatch; it is not a substitute for release-artifact signing. Entries bind exact source and target Server Build Identities, Connector Identity, semantic capability key and role/type signature, and evidence-suite revision. Configuration may disable a qualified capability but cannot add or broaden one. Phase one has no wildcard or nearest-version positive matching: zero matches block and multiple matches invalidate the Manifest at startup. Target Schema Plans retain the manifest digest, and `cdc doctor capabilities` displays its exact entries and evidence revisions. New positive support ships through a connector release.

Validated configuration is encoded as Protobuf and written to `cdc.<deployment_id>.control.v1`. Immutable Configuration Revisions and mutable desired-version pointers use different keys so Kafka compaction retains the revisions needed to interpret historical changes. The Desired Configuration is approved but may still be pending; each worker reports the Effective Configuration that actually governs it. Records contain only `env://NAME` or absolute `file://path` secret references.

One immutable Deployment ID and a deployment-level topic prefix namespace every Kafka object. Operators cannot choose individual generation topic names. A generation uses `cdc.<deployment_id>.<stream_id>.<generation_id>.events.v1`, `.schema.v1`, and `.checkpoint.v1` under the configured prefix; full immutable IDs, rather than mutable labels, form the names. The Configuration Revision and Generation Baseline store the resolved names. Changing the Deployment ID, prefix, generation ID, or any resolved topic name is replacement, not a hot edit.

`cdc config plan` performs strict syntax, topology, Kafka, database, permission, and continuity checks and reports both a canonical digest and the environment's current monotonic `control_version`. `cdc config apply` must supply that expected version and digest; a stale plan is rejected rather than merged or force-overwritten. Apply writes the complete bundle as `PENDING` in one Kafka transaction. Workers revalidate it, retain their old Effective Configuration until a safe boundary, and report `EFFECTIVE`, `REJECTED`, or a still-retrying `PENDING` state. Superseded and retired revisions remain immutable.

## Activation

Retry limits, logging settings, Transport Envelope limits, environment-observation intervals, and Secret References are hot settings. Capture Scope, Route Projection, and name mappings activate between complete source transactions. Deployment identity and topic prefix, entity IDs, database kinds, event-contract major versions, Kafka clusters, Capture Stream Generation IDs, generation topics, and the generation transactional producer identity are identity-bearing and require replacement rather than in-place mutation.

A Generation Activation is the first committed transaction in a generation. One stable producer with transactional identity `cdc.<deployment_id>.<stream_id>.<generation_id>.capture.v1` atomically writes the `GenerationActivated` Synthetic Transaction, Generation Baseline and complete Schema Anchor, initial Source Environment Epoch Definition, and initial Capture Checkpoint across the generation's three topics. Ordinary source events cannot appear first. A replacement worker initializes the same transactional identity so Kafka fences an obsolete producer; a fenced worker exits and never chooses a new identity.

Every Change Event carries its effective capture revision and Capture Scope revision. A Capture Scope change is a synthetic control transaction containing `CaptureScopeActivated`; the marker, new Capture Checkpoint, and effective revision status are published atomically before changes under the new scope. A Route Revision names an Effective Source Cursor. Its Sink drains older events under the old Projection and records the new revision in target Replication Metadata at the boundary. Mapping changes require the new target structure and baseline to pass preflight.

Source endpoints may change under the same Source identity only when Source Incarnation and cursor continuity are proven. Sink endpoints may retain identity only when Replication Metadata and expected target fingerprints prove the same logical Sink. Otherwise operators create new entities. Removing a captured object is rejected while an Effective Route still selects it unless one configuration bundle coordinates both removals; historical schemas and events remain retained.

Before reading beyond a complete Source Cursor, a changed source Server Build Identity, Semantic Environment Fingerprint, or Connector Identity pauses capture. The worker re-runs preflight, validates log continuity, and reconciles all current definitions with Schema History. When continuity, definitions, and the exact transition boundary are proven, Source Incarnation is preserved and an immutable Source Environment Epoch Definition plus a `SourceEnvironmentChanged` stream-control Synthetic Transaction start the new epoch before events produced under it are published. Every event carries its epoch reference. Polling detects but does not timestamp an otherwise unlogged setting change. An uncertain unpublished interval is discarded back to its last safe Capture Checkpoint; an uncertain already-published interval terminates that Capture Stream Generation and requires a new baseline. An unlogged definition difference blocks rather than being labeled an upgrade.

A normal Sink worker first plans the complete Transaction Batch under one Sink Transaction Plan and establishes its selected Sink Session Profile. Its Sink Apply Transaction then takes a shared lock on the Sink metadata row, verifies `ACTIVE`, Target Environment Epoch, and Sink Epoch Fence, and takes an exclusive lock on its Route row to verify Route Fence and Kafka coordinate. Both locks remain through commit. A changed Sink Server Build Identity, Semantic Environment Fingerprint, or Connector Identity takes the Sink row exclusively, waits for existing shared holders, and commits `REQUALIFYING`, a fresh Requalification Attempt, and an incremented Sink Epoch Fence before revalidating every Route targeting that Sink. The attempt stores an unguessable ID, Worker owner, target-database-time lease, candidate environment digest, expected old epoch, and fence. Its lease defaults to 60 seconds, renews every 20 seconds, and is configurable from 30 seconds through 10 minutes; validity is always evaluated against target-database time. New apply transactions cannot pass the state and fence check. The owner renews the lease while it re-runs capability checks and verifies Replication Metadata, Sink Session Profiles, and expected target definitions. A failed renewal immediately removes the Worker's right to complete. After lease expiry another worker may take the Sink row exclusively, create a new attempt, increment the fence again, and restart all checks. A completion metadata transaction reacquires the Sink row exclusively, verifies the exact attempt, owner, unexpired lease, candidate digest, `REQUALIFYING` state, and fence, and then takes affected Route rows in stable Route ID order. It creates one Sink-scoped Target Environment Epoch, updates each Route's epoch reference at its unchanged Kafka coordinate and Route Fence, and restores `ACTIVE`. A stale owner cannot complete. Only after that transaction commits may Routes resume; failure leaves the Sink fenced in `REQUALIFYING`. The transition is audited and never injected into the source Capture Stream. No Configuration Revision can waive a missing positive qualification; changing either endpoint to a logically different database requires a new Source or Sink identity under the existing continuity rules.

The MySQL Source Logging Contract is a validated operational prerequisite: all committed in-scope writes must appear in the retained binlog, including administrative and application writes. Initial activation requires an audited Source Logging Attestation bound to the Source, Source Incarnation, Capture Scope revision, and writer-policy digest. It has no arbitrary wall-clock expiry. A new Source identity or Incarnation, Source endpoint replacement, Scope expansion, writer-policy change, or known or suspected violation invalidates it and requires a new attestation; worker restart and semantically irrelevant configuration edits do not. The CLI reports current facts as observed, operator-attested, or unverifiable; it never presents the attestation as database proof and warns that `sql_log_bin=OFF` can create undetectable gaps. A violation blocks lossless continuation until independent reconciliation or a new baseline; ordinary retry cannot manufacture an absent event.

Each connector supplies a fixed, versioned Environment Profile whose requirements are classified as build identity, continuity identity, semantic fingerprint, required precondition, event-validated, session-profile, or operational-only. Scope and Route changes do not alter that field set. Environment checks run at startup, reconnect, Schema Anchor, native format-description or rotation boundaries, before and after relevant DDL stabilization, and periodically at a default 30-second interval subject to a connector lower bound. Health reports the last successful observation and digest. Periodic observation is detection, never evidence of the exact Source Cursor at which an unlogged change occurred.

`TRANSIENT` and `REPLAYABLE_IMPLEMENTATION_GAP` Capture blocks may resume from the previous Checkpoint when their stated prerequisites are restored and exact source bytes remain available. Phase one does not copy native Binlog into a second durable archive. Separate `capture_recovery_objective` and `route_recovery_objective` values default to seven days. Exact activation blocks when observable source-log or Kafka retention is lower than its applicable objective or cannot be verified. At runtime the worker monitors the required earliest coordinate and configured expiration policy and reports `OPEN`, `AT_RISK`, or `EXPIRED`; a retention reduction marks `AT_RISK` and alerts without stopping forward progress, while an expiration estimate remains advisory because an administrator can purge logs early. When exact bytes or events actually expire, the original block cause remains recorded but the generation or Route becomes `RESNAPSHOT_REQUIRED`. `IRRECOVERABLE_SOURCE_EVENT` and `PUBLISHED_INTEGRITY_FAULT` require a new Generation Baseline immediately. A new generation receives a fresh UUID and dedicated event, schema, and checkpoint topics; old topics become read-only and existing Routes remain bound to the old generation in `RESNAPSHOT_REQUIRED`. Phase one reports this terminal recovery requirement but cannot perform an automatic data baseline.

Configuration rollback republishes a historical revision as a new Desired Revision, repeats preflight, and takes effect only at a future boundary. It does not reverse data or DDL already applied under the superseded revision.

## Secret rotation

`cdc secrets reload` rereads `file://` references, completes or rolls back in-flight database work, validates fresh connections, and only then replaces old pools. Failed credentials leave working old pools intact; if those are no longer usable, processing reconnects without advancing its Checkpoint. Environment variables of an existing process are not considered reloadable, so rotating an `env://` secret requires a worker restart. Auditing records references and outcomes, never secret values or hashes.

## Assignment and lifecycle

Runtime workers select entity IDs or labels explicitly. Capture Streams have one assigned worker in phase one; Sink workers may use consumer-group ownership and a target Route Fence for standby takeover. Removing an entity from an input file does not delete it. Operators retire it explicitly, preserving topics, Checkpoints, and Replication Metadata. A separate audited purge performs eventual physical deletion.

## Route start

A new route must declare one Route Start Point:

- `EARLIEST_AVAILABLE`, at the earliest retained complete transaction;
- `LATEST`, at the first transaction activated after route creation;
- `AT_SOURCE_CURSOR`, resolved and validated against the event stream;
- `AT_KAFKA_OFFSET`, an advanced recovery mode that also requires the expected Source Cursor.

The resolved point must be a `TX_BEGIN` boundary. The CLI rejects an arbitrary offset inside a transaction or a point whose continuity cannot be proven.

Every Capture Stream Generation additionally requires one source-side Generation Baseline. Every Route requires its own Route Baseline at the resolved start boundary: `EXACT_EXTERNAL_BASELINE` records a complete External Baseline Attestation, while `FUTURE_ONLY` starts the Route as `DEGRADED` and explicitly disclaims pre-existing-row equivalence. Future-only apply remains strict: a missing target row or before-image mismatch blocks, and the Sink never upserts or ignores a DELETE automatically. Phase one validates cursor, schema, mapping, environment, target definitions, and evidence identities but does not copy or compare all baseline rows. A Route cannot change generation or baseline in place; rebuilding creates a new Route identity and preserves the failed Route as history.

Route activation is authoritative only after one target metadata transaction locks and validates the Sink state and fence and inserts the new Route record with its baseline digest, initial source and Kafka coordinates, configuration and environment identities, and initial Route Fence. It performs no replicated business DML. The consumer-group offset is committed afterward; after an uncertain outcome the worker reads target Replication Metadata rather than trusting Kafka's offset.

## Bootstrap and privileged operations

`cdc bootstrap kafka` derives generation topic names, creates them with an administrative Kafka identity, and verifies their partition count, compaction and retention policy, transaction and record-size limits, and ACLs before activation; runtime identities cannot create or delete topics. Topic creation alone does not bind or activate a generation. The first transactional Generation Activation supplies the immutable Generation Topic Binding across all three topics. An existing nonempty topic is accepted only when its retained records and control definition match the Deployment, stream, generation, topic role, and contract major exactly; an unknown or conflicting topic is never adopted or rewritten. `cdc bootstrap target` creates the one permitted target metadata table when supplied a DDL-capable database identity. That table holds typed Sink, epoch, and Route records; no additional target object is needed for Sink Epoch Fencing. A DML-only runtime requires the table to exist. Metadata schema upgrades are explicit and require affected routes to be paused.

The append-only `cdc.<deployment_id>.audit.v1` records configuration publication and activation, Source Logging Attestation and invalidation, Generation and Route Baselines, Capture recovery classification and Recovery Window changes, generation termination and creation, Requalification Attempt ownership and takeover, pause and resume, Schema Adoption, force-skip, retirement, purge, actor identity, reasons, entity IDs, configuration digests, and outcomes. It defaults to one year of retention and contains neither secrets nor row data. The POC identifies actors by operating-system username and delegates authority to host permissions, Kafka ACLs, and database grants. High-risk commands require the exact entity or event identity, a reason, and explicit confirmation.
