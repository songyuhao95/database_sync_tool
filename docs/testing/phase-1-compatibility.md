# Phase-one compatibility scope

The POC uses exactly the three available Oracle MySQL Community Server instances: one 5.7 instance, one 8.0 instance, and one 8.4 instance. Qualification records the exact server version and build reported by each instance and, where containerized, pins the immutable official-image digest. Floating major-series tags are bootstrap conveniences only and are not qualification identities. The POC does not claim qualification of other patch releases or of MariaDB, Percona Server, Aurora MySQL, HeatWave, or another MySQL-protocol distribution; those are rejected as distinct future connector kinds.

## Direction matrix

All nine source-to-target directions are exercised among those instances:

| Source | Targets |
| --- | --- |
| 5.7 | 5.7, 8.0, 8.4 |
| 8.0 | 5.7, 8.0, 8.4 |
| 8.4 | 5.7, 8.0, 8.4 |

For a same-version direction, isolated source and target databases share the one available server instance. The Capture Scope excludes the target database and the tool metadata table so applied changes cannot feed back into the test stream. These cases validate connector and data semantics but do not simulate independent same-version server failure.

## First vertical slice

Implementation starts with MySQL 8.0 to MySQL 8.0 using a file-position cursor and the combined runtime role. Starting with empty source and target databases, the test creates a table after capture begins, applies DML and supported table DDL through Kafka, and injects failures around source publication and target commit. Correct target contents, ordering, resume coordinates, and Exactly-once Effect are release gates; performance is measured under a documented benchmark environment but is not a POC release claim.

## DDL qualification

The nine-direction suite distinguishes positive compatibility from intentional blocking. It covers explicit and `LIKE` table creation, every allowlisted column and BTREE-index operation, key and constraint transitions, table rename and drop, No-op Schema Changes, and Table Reset. Negative cases cover CTAS, temporary and partitioned tables, unsupported expressions and indexes, non-InnoDB engines, charset conversion, physical or security options, mutable `AUTO_INCREMENT` counter changes, incompatible collation or visibility semantics, and CHECK enforcement that cannot be preserved.

Foreign-key cases include exact in-scope constraints, blocked out-of-scope dependencies, explicitly degraded omission of only `RESTRICT` or `NO ACTION`, and mandatory preservation of `CASCADE` and `SET NULL`. DDL crash injection exercises each target version. MySQL 5.7 enables only single-object operations whose observed interrupted states are deterministically reconcilable; a state matching neither the expected before nor after definition is a blocking result rather than a successful retry.

Lineage tests rename tables and columns, reorder columns, truncate tables, drop and recreate the same name, clone with `LIKE`, remove and restore Route Projection, and remove and re-add Capture Scope. Replaying the same source history must reproduce identical lineage IDs, while a genuinely new object must never inherit an old identity. Reset recovery injects failure before execution, during target execution, after successful execution, after empty-state verification, and before metadata advancement; every recoverable case converges by guarded reexecution without allowing a later event to pass.

MySQL 5.7 and any exact MySQL 8.0 version before 8.0.16 verify that ignored CHECK text remains Native Statement Evidence but is absent from the anchored Table Definition, Schema Fingerprint, and generated target DDL. Diagnostics verify that raw SQL is hidden by default and ordinary runtime logs contain neither its bytes nor comments.

Schema contract tests publish definitions and referencing events in the same Kafka transaction while independently delaying either topic consumer. Apply must wait for a delayed valid definition and block for a missing, corrupt, conflicting, or wrong-lineage definition. Golden canonical vectors verify that lineage, rename, drop/recreate, element replacement, source versus mapped target names, and Schema Context changes produce the expected distinct fingerprints.

Definition-adapter tests compare `INFORMATION_SCHEMA`, parsed `SHOW CREATE`, `SHOW INDEX`/`STATISTICS`, foreign-key catalog pairs, and CHECK catalog pairs on each of the three exact instances. They inject transient and persistent disagreements to prove retry-then-block behavior. Golden vectors distinguish absent, empty, and explicit-null fields; preserve non-ASCII identifier and comment bytes with their encodings; prove that display text, statistics, and current `AUTO_INCREMENT` counters do not affect fingerprints; and prove that case folding, Unicode normalization, or trimming is never performed.

Schema-element tests keep Semantic Key and Access Index lineages independent, including key-backed index replacement and rename. They cover prefix units and direction, external foreign-key references without fabricated lineage, system-generated invisible primary keys, and Opaque Native Expressions that must block every generated cross-version plan while remaining auditable.

Effective-definition tests exercise MySQL's silent normalization, explicit versus server-derived defaults, nullable and non-nullable absent defaults, legacy `TIMESTAMP` behavior under both `explicit_defaults_for_timestamp` settings, and catalog disagreement after live DDL. Expected definitions reflect server-effective semantics rather than submitted spelling.

Expression tests preserve operand order and prove that constant folding, commutative sorting, implicit casts, and algebraic simplification never enter canonicalization. Capability cases are keyed by role, operand/result types, and the exact source-target pair. The initial allowlist receives positive and negative execution vectors; nondeterministic defaults, unqualified operations, and incompatible general expression defaults block. DML tests prove that materialized row values are applied without retaining or re-evaluating the source assignment expression.

Delivery-gate tests first prove that unknown-but-bounded expressions survive as Opaque Native Expressions without changing their bytes or digest. They distinguish a safely decodable table, where capture continues and only an incapable Route blocks at its schema boundary, from an expression that makes definition or row interpretation unsafe, where the Capture Stream itself must block. Each subsequently enabled AST family adds canonical vectors before any positive target capability entry is accepted.

Row-image tests inspect native column bitmaps rather than assuming that `FULL` supplies every generated result. Every ordinary writable column must become `VALUE` or `NULL`; a generated column may become a Generated Observation or `NOT_CAPTURED`. Sink tests prove that defaults, automatic timestamps, invisible ordinary values, and explicit identity values are bound from the source result, generated columns are omitted, available Generated Observations are checked before commit, and no absent observation causes a source-row query.

Source-logging tests require global `ROW` and `FULL` at preflight, then generate actual row events, session-overridden statement DML, minimal and `NOBLOB` images, complete and invalid partial JSON updates, and relevant versus provably irrelevant Query Events. The native event and bitmaps decide acceptance. In-scope statement DML or any missing required ordinary value blocks Capture before publication, while a valid partial JSON patch over a complete before document produces one complete after Logical Value. Activation tests require a Source Logging Attestation bound to Source, Source Incarnation, Capture Scope revision, and writer-policy digest and expose each fact as observed, operator-attested, or unverifiable without presenting the attestation as database proof. Restart and unrelated edits retain it; endpoint or Incarnation replacement, Scope expansion, writer-policy change, and suspected violation invalidate it. A documented negative test performs an in-scope write with `sql_log_bin=OFF` and proves that no connector can observe or recover it; the run invalidates the attestation and is classified as a Source Logging Contract violation rather than successful lossless capture.

Generated-observation tests compare through Column Conversion Plans rather than SQL equality and cover exact decimal scales, negative zero and floating bits, byte-distinct collation-equal strings, typed JSON numbers, spatial SRIDs, nulls, generated-key locators, and GIPKs as ordinary system-origin identities. Every supplied observation is checked immediately after its Row Change and before commit. A transaction that updates the same row twice proves that the first intermediate observation is not hidden by the second update. Cross-row batching is accepted only with a proof of disjoint candidates and no intervening mutation; batching and immediate fallback must otherwise produce identical decisions. A mismatch rolls back all rows in the source transaction.

Retry-classification tests inject a deadlock, lock timeout, connection loss, deterministic generated mismatch, missing validation row, and locator ambiguity. Transient cases replay the entire source transaction and every observation without partial metadata advancement. Deterministic cases block as Target Capability Failures, while retry-budget exhaustion remains explicitly retryable operational state.

Capability manifests are generated only from the pinned three-instance matrix and identify exact server and connector builds plus evidence-suite revision. Upgrading or replacing any instance invalidates its entry. Golden vectors reproduce the canonical manifest bytes and SHA-256 digest, startup rejects an accidental embedded mismatch, and documentation does not represent that self-check as malicious-tamper protection. Lookup tests reject wildcard or nearest-version matches, zero matches, and duplicate applicable entries. Tests also assert that Opaque Native Expressions, Unsupported Features, Capture Block Reasons, Target Capability Failures, and Known Omissions produce non-overlapping records and state transitions. An in-scope Unsupported Feature blocks publication of its definition even when no Route currently selects it; an out-of-scope occurrence is ignored only with an irrelevance proof.

Environment-change tests independently vary Server Build Identity, Semantic Environment Fingerprint, and Connector Identity between complete transactions. Proven source log continuity, unchanged definitions, and an exact transition boundary create a new Source Environment Epoch without changing Source Incarnation. The immutable definition and `SourceEnvironmentChanged` transaction are visible before the first event under the new epoch, every event binds the correct definition digest, and a Route starting later can resolve it without replaying the marker; unlogged schema drift blocks without either record. An unlogged non-self-describing change detected before publication discards the uncertain spool to the last safe Checkpoint, while detection after publication terminates the generation and requires a new baseline rather than appending a backdated marker. A replacement generation must use a fresh UUID, event/schema/checkpoint topics, deterministic identity domain, initial environment definition, and Schema Anchor; old topics remain read-only and existing Routes remain bound to the failed generation in `RESNAPSHOT_REQUIRED`. A Sink with multiple Routes first enters `REQUALIFYING` and increments its Sink Epoch Fence. A delayed stale Worker must fail its next commit. Qualification then records one Sink-scoped Target Environment Epoch and each Route's exact Kafka coordinate and fences in a metadata-only transaction and resumes only afterward. Failure remains fenced. Distribution spoofing, an unrecognized build, a stale manifest digest, or an operator attempt to broaden capability is rejected.

Environment-authority tests reproduce each connector's fixed Environment Profile and separate role-wide Semantic Environment Fingerprints from DDL Parse Context, native row-event format and column bitmaps, and Sink Session Profiles. Golden classifications assign every requirement to exactly one of `BUILD_IDENTITY`, `CONTINUITY_IDENTITY`, `SEMANTIC_FINGERPRINT`, `REQUIRED_PRECONDITION`, `EVENT_VALIDATED`, `SESSION_PROFILE`, or `OPERATIONAL_ONLY`; omissions and contradictory assignments invalidate the Manifest. Scope and Route changes do not alter the Environment Profile's field set. Observation tests run at startup, reconnect, Schema Anchor, format-description and rotation boundaries, relevant DDL stabilization boundaries, and the configurable periodic cadence whose default is 30 seconds. They prove that polling reports detection time rather than inventing a source-event boundary and that event-level validation still runs between polls. Pool tests mutate each target session variable between checkouts and prove that the complete profile is restored and read back before `BEGIN` or the connection is discarded. A narrowly relaxed profile uses a dedicated connection that is destroyed afterward.

Sink-fence concurrency tests run two Routes concurrently under shared Sink-row locks, then request requalification. The exclusive transition waits for in-flight commits, raises the Sink Epoch Fence before new work can enter, locks Route rows in stable ID order, and rejects delayed stale workers without serializing normal Route execution behind an exclusive Sink lock.

Requalification-attempt tests crash an owner before validation, during lease renewal, and immediately before completion. Leases use target-database time, default to 60 seconds, renew every 20 seconds, and reject configuration outside 30 seconds through 10 minutes. An unexpired attempt cannot be stolen, an expired attempt can be replaced only by a new attempt ID and incremented fence, and a stale owner or one whose renewal failed can neither renew nor complete. Takeover restarts all checks from the candidate environment rather than trusting partial predecessor work, and only an exact unexpired attempt may atomically create the Target Environment Epoch and restore `ACTIVE`; tests use a controllable clock rather than wall-clock sleeps.

Sink-transaction-plan tests pre-scan transactions containing ordinary writes, qualified invalid temporal values, and incompatible session requirements. One immutable plan and exactly one verified Sink Session Profile cover the complete transaction; no worker changes session state between Row Changes. Manifest fixtures prove unique subset-minimal profile selection and reject zero matches, equally minimal candidates, incomparable candidates, and any attempted runtime fragment merge. A qualified relaxed transaction uses one dedicated connection that is destroyed after commit or rollback, while incompatible requirements fail before DML. Retry regenerates the same plan digest, and a changed definition, environment epoch, capability, fence, or Kafka coordinate prevents execution. Successful Replication Metadata contains only bound identities and plan, profile, and Manifest digests; target metadata, audit records, and ordinary logs are checked for absence of full DML plans, rendered SQL, bound parameters, and row values.

Capture-recovery tests classify representative failures as `TRANSIENT`, `REPLAYABLE_IMPLEMENTATION_GAP`, `IRRECOVERABLE_SOURCE_EVENT`, or `PUBLISHED_INTEGRITY_FAULT`. The first two resume only from the previous Capture Checkpoint while exact bytes and prerequisites remain available; the latter two never resume the generation. Fixtures vary the version-specific Binlog expiration settings, earliest retained file, log rotation, and manual purge to drive `OPEN`, `AT_RISK`, and `EXPIRED` without treating a predicted expiry as proof. They verify that phase one has no durable raw-Binlog archive and that an expired replayable gap retains its original diagnostic while the generation becomes `RESNAPSHOT_REQUIRED`. Tests also prove that a published integrity fault cannot be hidden by a late control marker and that no recovery path advances a Checkpoint past an unpublished blocked transaction.

Baseline tests keep source-owned Generation Baselines separate from target-owned Route Baselines in one-to-many topologies. They validate exact transaction cursors, Schema Anchor and environment references, Kafka coordinates, definitions, mappings, evidence digests, and immutable identities for both `EXACT_EXTERNAL_BASELINE` and `FUTURE_ONLY`. Exact activation rejects a missing Baseline ID, source snapshot or backup reference, external load completion identity, actor, reason, or evidence SHA-256 and confirms that no evidence content or row data enters ordinary logs. A new generation without its baseline cannot activate; a new Route cannot claim exact consistency from a future-only baseline; and rebuilding creates a new Route identity while preserving the failed Route and its `RESNAPSHOT_REQUIRED` history. A future-only Route starts `DEGRADED`; an UPDATE or DELETE for a missing pre-existing row blocks without upsert or ignore behavior. The suite explicitly proves that operator-attested external row alignment is reported as a condition, not as tool-verified data equality.

Kafka-bootstrap tests run against the deployed Apache Kafka 3.7.2 KRaft broker using `rdkafka` 0.39.0 and derive topic names only from the deployment prefix and immutable Deployment, stream, and generation IDs. They validate the events topic's single partition, schema/checkpoint compaction, configured retention, record and transaction limits, single-node internal-topic settings, and ACLs before generation activation. The first committed Kafka transaction must contain `GenerationActivated`, the Generation Baseline, initial Source Environment Epoch Definition, complete Schema Anchor, and initial Capture Checkpoint across all three topics; no second event-envelope type or ordinary event may precede it. A nonempty topic is reusable only when its retained records and control definition exactly match Deployment, stream, generation, role, and contract major; unknown, conflicting, label-derived, or individually overridden names are rejected. Retired generation topics remain read-only until an explicit audited purge.

Kafka-transaction tests use the stable `cdc.<deployment_id>.<stream_id>.<generation_id>.capture.v1` transactional identity with `acks=all`, idempotence, and `read_committed` consumers. Starting a replacement producer fences the predecessor; the stale Worker treats its next fenced result as fatal and never retries under a different identity. Failure injection before send, between topic writes, during commit, after commit response loss, and during abort proves that events, definitions, and Capture Checkpoint become visible together or not at all. Kafka 4 transaction protocol version 2 is disabled from the qualification assumptions.

Recovery-objective tests default Capture and Route objectives to seven days. Exact activation rejects lower or unverifiable observable retention. Runtime retention reduction marks `AT_RISK`, emits an alert, and continues forward progress; manual deletion of an actually required Binlog or Kafka record produces `EXPIRED` and `RESNAPSHOT_REQUIRED`. Capture and Route tests verify that source retention cannot substitute for missing generation events and Kafka retention cannot recreate missing source history.

Route-activation tests inject crashes before target metadata `BEGIN`, before insert, after insert but before commit, after an unknown commit response, and before Kafka offset acknowledgement. The metadata-only transaction verifies Sink state and fence and records the Route Baseline digest, initial Source Cursor, Kafka input and next offsets, configuration and environment identities, and initial Route Fence without replicated DML. Every retry resolves state from target Replication Metadata; Kafka offsets never override a committed target coordinate.

GIPK tests run with generation and metadata visibility settings varied on every supporting qualified instance. They verify explicit `SYSTEM` lineage, prevention of accidental target-generated keys, and blocking whenever the target cannot reproduce invisible identity semantics.

Target-plan tests verify deterministic schema-scoped constraint names, raw-path collision rejection, `EXECUTE_DDL` versus `VALIDATE_ONLY`, plan-digest reproduction after restart, and all three recovery classes. Missing Kafka recovery input, a changed route revision, a changed plan digest, mixed multi-object before/after state, or a target catalog that cannot be assigned the expected lineage must block without executing SQL.
